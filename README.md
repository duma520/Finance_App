## 第一部分：写给所有人——3 分钟看懂这个软件

### 1.1 这是什么？

**人民币收支管理系统**（程序文件名 `Finance_App.py`）是一款运行在 Windows 电脑上的**个人/家庭记账软件**。它用 Python 3.10 编写，界面用 **PySide6（Qt6）**，数据存在本地的 SQLite 数据库里，**不联网、不上传、不收集你的任何数据**。

一句话总结：**它帮你把"钱从哪来、花到哪去"记清楚，并且能自动帮你把银行发来的短信/微信提醒变成一条记账记录。**

### 1.2 它适合谁？

| 人群 | 能用来干什么 |
| --- | --- |
| 学生 | 记录生活费收支，看看钱花在哪 |
| 上班族 | 记工资、房租、餐饮、交通，做月度预算 |
| 家庭主妇/主夫 | 管理家庭多个账户（现金、银行卡、支付宝、微信） |
| 个体户/小微企业主 | 记录经营收支、借款还款、多账户余额 |
| 财务人员 | 导出 CSV/Excel 做进一步分析 |
| 程序员 | 阅读源码、二次开发、学习 PySide6 + SQLite 项目结构 |

### 1.3 它有什么特色？

1. **完全本地**：数据在你自己的电脑上，加密可选。
2. **多用户**：一台电脑可以给全家人分别记账，互不干扰。
3. **交易提醒自动填写**（★ 最大亮点）：把银行公众号/支付宝/微信的交易提醒**粘贴进去**，自动识别金额、商户、日期、收支类型，一键填好。
4. **窗口大小、设置自动记住**：不用每次打开都重新调。
5. **数据变动后自动刷新**：选"最近一周"，加了新记录也能立刻看到。
6. **有冒烟测试**：六套冒烟测试 + 五个断言探针，共 **580 项**断言（其中 `smoke_test_balance_v69.py` 是 **v6.9 余额专项对账**：三条不变式 + 10 个场景；`_probe_rec_time_v72.py` 是 **v7.2/7.3 时间专项**，19 项；`_probe_recalc_v74.py` 是 **v7.4 重算覆盖专项**，33 项；`_probe_eff_v75.py` 是 **v7.5 有效账户归属专项**，27 项；`_probe_page_v76.py` 是 **v7.6 列表分页专项**，30 项），保证改动不破坏老功能；还有全机数据只读体检脚本 `audit_all_dbs.py`、`audit_rec_time.py`、写库点静态审计 `_audit_recalc2.py`，以及 v7.0 的界面探针脚本（验证按钮该藏时藏得住）。

### 1.4 我需要什么才能运行它？

- 一台 Windows 电脑（Win7 及以上，推荐 Win10/Win11）
- 如果用打包好的 exe：**什么都不用装**，双击就能用
- 如果从源码运行：需要 Python 3.10 + PySide6 等依赖（见第三部分）

### 2.1 每个版本的白话解释

**v4.0**：以前你设置了"自动备份保留 30 份"，关掉软件再打开，又变回默认了。这个版本开始，所有设置都存进数据库，重启后还在。窗口大小也开始被记住。

**v4.1**：以前收到银行短信，要手动抄金额、抄商户、抄时间。这个版本开始，你把短信内容**整段粘贴**到添加记录弹窗里，点一下"解析并填写"，金额、描述、日期自动填好，连"收入还是支出"都帮你选好。

**v4.2**：有些银行 App 的提醒是分行写的（"交易金额    人民币200.00"），标签和值之间是**空格**不是冒号。这个版本开始支持这种格式。而且如果提醒里没有"商户"，就用"交易附言"当描述。

**v4.3**：以前搜索框和 7 个筛选控件全挤在一行，分类名一长（比如"招商银行储蓄卡（尾号1234）"），窗口就被撑到 1400 多像素，缩都缩不下去。这个版本改成三行，窗口最小宽度从 1400 降到 735。

**v4.4**：以前窗口大小只在**正常关闭**时才保存，如果程序崩溃、被任务管理器强杀，尺寸就丢了。这个版本改成"你拖动完 800 毫秒后就自动保存"，不依赖正常退出。

**v4.5**：修 4.4 的一个 Bug——4.4 虽然实时保存了，但启动恢复时，程序内部有个"更新日期范围"的步骤会**顺手把默认窗口尺寸写回数据库**，导致你上次存的尺寸被覆盖。这个版本先读尺寸、再干别的，并且恢复期间禁止写尺寸。

**v4.6**：你选了"最近一周"，起止日期是**选的那一刻**算出来的（今天-7 到 今天）。如果程序开着过了一夜，第二天新增记录（日期是"今天"），就超出了旧的"到"，刚加完看不到。这个版本改成每次刷新都按当前时间范围重算。

**v4.7**：你粘贴"交易附言 银联无卡转账,对手户名-李红玲"，结果只填进去"银联无卡转账"，后面被吃了。原因是附言用了**商户的清洗器**，那个清洗器会在逗号处截断。这个版本给附言单独写了一个清洗器，**不按逗号切**，长度上限从 30 字放宽到 100 字。

**v4.8**：筛选栏字段宽度不统一（日期框 212、下拉框 118），标签也不对齐，看着凌乱。这个版本把筛选控件装进一个圆角面板，两行用**同一个网格**排，标签右对齐，7 个字段统一 118 像素宽。还加了"重置"按钮。

**v4.9**：新增"工具 → 设置…"对话框。第一个选项是"添加记录后自动滚动到列表底部"——开了之后，每次加完记录，列表自动滚到最底，方便看到刚加的那条。**设置项点选即保存**，没有"保存"按钮。

**v5.0**：有些提醒里既没有商户、也没有附言，只有"交易类型：收入（尾号4132账户）"这么一行。以前这种会解析不出描述，现在就用"交易类型"后面那段文字当描述。

**v5.1**：给"添加记录"弹窗加了两个显示开关——"关联借款"下拉框和"添加收据"按钮，不需要时可以隐藏，弹窗更清爽。

**v6.0**：把底层界面库从 PyQt5 整体换到 PySide6（Qt6）。这一步是为了跟上新系统和 Python 3.10，功能行为不变，但**旧版本的 exe 和新版的编译脚本不能混用**。

**v6.1**：修掉了程序启动时控制台刷屏的那句"dataChanged() called with an invalid index range"——起因是筛选后往表格里写第 11 列时越界。

**v6.2**：有些银行提醒的"交易说明"里写的是"点击查看余额及明细"这种引导语，不是真正的说明。以前会把它当描述填进去，现在识别为占位语，回落到"交易类型"那一行。

**v6.3**：设置里新增"定期交易"显示开关；同时把"交易提醒信息"区块压扁——粘贴框 96 → 68 像素，状态文字改单行（完整内容在鼠标悬停提示里），弹窗不再被顶高。

**v6.4**：「添加记录」弹窗不再写死 680×640，改成按内容自适应（实测 421 像素高），不再空出一大片。

**v6.5**：把弹窗上下拉高时，多出来的高度**全部给粘贴框**（拉到 640 时粘贴框从 68 变成 287 像素），方便粘贴长短信。

**v6.6**：「添加记录」弹窗里，类型选"还款"时会出现**「一键还款」**按钮，点一下自动把第一笔待还借款的**剩余应还金额**填进金额框并直接确定，不用手算。

**v6.7**：主界面加**「一键批量还款」**按钮。点开列出所有待还借款，可以全选、多选、全不选，确定后逐笔按剩余金额自动还款并标记结清。

**v6.8**：数据库备份范围扩大——`finance_master.db`（用户清单）每次改动后自动备份，`launcher.db` 随启动/每小时/退出比对。都是**先比内容、变了才备**，保留最近 30 份。

**v6.9（重要，建议所有人都升级）**：你之前的怀疑是对的——**"一键还款"之后账户余额确实会算漏**。根因是程序里存在两套互不通气的余额算法：

- 总账口径不带账户，算得对；
- 账户口径带 `account_id`，但"一键批量还款"把还款记录的 `account_id` 硬编码成了 **-1**（一个根本不存在的账户）。

结果就是：**借款时钱从账户 A 扣掉（账户 A 少 X），还款时却记到 -1 上（账户 A 一分没回来），于是账户 A 永久偏负 X**，而总账看着是对的。

这个版本做了三件事：

1. **立统一算法**：账户余额 = **初始余额 + 流水净额**，公式只保留一处定义，所有增删改、批量还款、标记结算、超额还款调整、定期交易、撤销全部走同一个收尾入口 `refresh_after_change`，不再各写各的；
2. **新增"初始余额"字段**：以前新建账户填的"初始余额"会被下一次重算直接抹掉（比如你建账户时写 1000，一记账就变 0），现在单独存起来，不再丢；
3. **修掉 18 项缺陷**，包括：批量还款不重算、还款记到表单当前账户而不是借款账户、**加密模式下撤销等于清空数据库**（这个最危险）、加密模式切用户/退出丢数据、加密备份是空壳、删除记录拿错账户、编辑换账户只算新账户、"标记已结算"按钮点完自己变回未结算、余额统计永远比账户余额少一截、定期交易执行时篡改历史日期。

顺带还做了一次**历史数据归位**：本机 2 个库里共有 82 笔被写进 -1 的还款记录（合计 3138.35 元），已按各自借款账户归位，账户余额从错误的负数恢复正确。归位脚本 `_scaffold\fix_legacy_account_id.py` 默认只演练不写库，写库前自动整库备份。

**v7.0（重要，建议所有人都升级）**：修一个很坑的问题 —— **你点「一键还款」，结果存进去的却是一条「账户结余」或「收入」**。

原因不在算钱，而在按钮：程序把这个按钮加进对话框按钮栏时，Qt 会自己把它显示出来，覆盖掉前面「只有选『还款』才显示」的设置。于是**不管当前是什么类型，这个按钮都看得见**。你点它的时候，类型还是上次用剩的（可能是「账户结余」「收入」「余额」），程序就照着那个类型把数据存进去了 —— 所以「一键还款」变成了「加一条账户结余」。

这个版本改了四件事：

1. **按钮只在「还款」类型下出现**，而且是在按钮加进按钮栏**之后**再设一次可见性（顺序反了等于没设）；
2. **点了「一键还款」先把类型强制切成「还款」**，切不过去就弹窗提醒「请先把类型选为『还款』」并中止 —— 绝不会再拿别的类型提交；
3. **「余额 / 账户结余 / 待还款合计」这三种一次性类型不再被记住**（下次打开弹窗一律回到「收入」），从源头减少误触；
4. 设置里关掉「关联借款」下拉框时，一键还款也能正常找到待还借款（以前会误报「没有可关联的借款」）。

已经存错的那条记录：到列表里找到它（类型显示「账户结余」或「收入」，描述是「截至 X 的账户结余」，或金额刚好等于某笔借款的剩余应还），**右键删除**即可；删掉后 v7.0 会自动重算余额对齐。

**v7.1（重要）**：**「类型」和「账户」现在真的能跨重启记住了** —— 上次选的是「支出 + 招商银行」，关掉软件再打开、再点「添加记录」，还是「支出 + 招商银行」。

以前为什么记不住？程序启动时会先把账户下拉框切到第一个账户（现金账户），这个「切一下」被保存逻辑当成了你的选择，**当场把你上次存的账户覆盖掉了**；等真正去读设置时，读到的已经是刚被写进去的默认值。类型之所以没事，是因为它的赋值在「开始监听变更」之前完成，不会触发保存。

这个版本改了四件事：

1. **加了一个「恢复期间别写库」的开关** —— 程序加载设置的那几秒里，任何控件的自动保存都被拦住，加载完再放开；
2. **账户按「编号」记，不只按名字记** —— 你把「银行2」改名成「招商银行」，下次打开还是它，不会因为找不到旧名字就退回现金账户；
3. **「添加记录」弹窗和主界面用同一套记忆**，弹窗打开时看到的就是你上次的选择；
4. **切换用户后各自记各自的** —— 以前切到另一个用户，类型/账户还沿用上一个人的，现在切过去就是那个用户自己上次的选择。

**v7.2（重要）**：**每条记录都有时分秒了**。列表里的日期现在显示成 `2026-11-21 16:31:06` —— 前面是日期，后面是标准「时:分:秒」。

为什么时间要单独存一列、不塞进「日期」那一列？因为 SQLite 只认到秒，一旦把 `2026-11-21 16:31:06` 整串塞进日期列，全项目所有按月统计会**静默变成 0，而且一个错误提示都不会有**，日期区间筛选也会把当天的记录全部漏掉。所以日期列**原封不动**保持 `2026-11-21`，时间单独存 `rec_time` 一列，显示时再拼起来。这样 30 多处按月统计、日期筛选、余额快照的 SQL **一行都不用改**。

这个版本改了五件事：

1. **手动添加能选时间**：「日期」旁边多了个时间框（默认当前时间），秒精确到整秒；
2. **粘贴交易提醒会自动带时间**：提醒里写 `2026-11-21 16:31:06`，就存成 `16:31:06`；只有到分钟的提醒按 0 秒；
3. **编辑记录能改时间**：双击那条记录，日期旁边同样有时间框；
4. **同一天内按时间排序**：以前同一天只能按录入顺序（id）排，现在 08:00 的记录排在 16:31 前面；
5. **导出带时间**：CSV / Excel 的「日期」列同样是 `2026-11-21 16:31:06`。

老数据（本机 18 个库共 4427 条）已经统一补成 `00:00:00`，也就是「那天 0 点」，显示起来是 `2026-11-21 00:00:00`，不影响任何统计。

**v7.3**：上一版曾把秒写成 4 位（`16:31:0600`、`00:00:0000`），这一版按你的要求**改回标准 2 位**（`16:31:06`、`00:00:00`）。升级时会自动把库里所有 10 位老值裁成前 8 位（`16:31:0600` → `16:31:06`），界面上再也看不到 4 位秒；本机 18 个库 4427 条已全部裁好。

体检/修复脚本在 `_scaffold\audit_rec_time.py`，默认只读演练，加 `--apply` 才写库（写前自动备份整库到 `backups\`）。

**v7.4（重要）**：**任何「添加 / 删除 / 编辑」操作做完，跟它相关的数字都当场重算，不会再出现「刚加完是这个数、过一会儿又变了」。**

v6.9 就立了规矩：所有操作收尾都走同一个函数 `refresh_after_change()`，由它一次性把余额、余额快照、账户结余、列表、统计全部对齐。但规矩立了不等于所有地方都遵守 —— 还有 **6 个入口偷偷绕过了它**：

1. 主界面添加「待还款合计」；
2. 「添加记录」弹窗里添加「待还款合计」；
3. 新增账户；
4. 编辑账户（改初始余额）；
5. 删除账户；
6. 从备份恢复数据。

这 6 处以前写完库只刷一下列表，**账户余额和「余额统计」快照不跟着变**。你看到的怪现象就是：加完一笔，界面上还是旧数字；过一会儿做了别的操作（那时才触发重算），数字又变了 —— 这就是多算、少算、漏算的来源。账户那三条更严重：「余额统计」快照 = **所有账户初始余额之和 + 截至当日的流水净额**，你新增 / 删除 / 改了初始余额，初始余额之和变了但快照没重算，**那个快照就永久是错的**。

这一版把 6 处全部改成走 `refresh_after_change()`，并且把 `update_future_balances()` 里手抄的两段「流水净额」SQL 收敛成同一个常量 `_NET_FLOW_SQL` —— 现在账户余额、总余额快照、统计三处**只可能用一种口径**，不会再出现「改了一处忘了另一处」。顺便：从备份恢复数据以前也只刷列表，现在恢复完余额 / 快照 / 统计一起对齐。

还加了两个自查工具（以后新加写库功能都要跑）：
- `_scaffold\_audit_recalc2.py`：把所有会写 `transactions` / `accounts` 的方法列出来，标出哪些没走重算入口；
- `_scaffold\_probe_recalc_v74.py`：33 项断言（静态接线 19 项 + 快照口径 7 项 + 端到端 7 项）。

**v7.5（重要）**：**你登记的东西一个字都没动，改的只是「怎么算」。**

以前版本留了个坑：一条「还款」到底算哪个账户，程序直接看她自己记的 `account_id`。可早年「一键批量还款」会把这个字段写成 `-1`（一个根本不存在的账户）。于是同一批钱在两边各算一半 —— **全库净额 0.00，账户净额却是 -1016.46**，账户加总永远对不上全库，新建账户结余自然算出个负数。

这一版引入「**有效账户归属**」（EFF）：**一条还款属于哪个账户，取决于它偿还的那笔借款在哪个账户**，不再看还款自己记的账户。只要借款↔还款的对应关系是对的（这个一直是对的），算出来的账户余额就一定和全库对得上。

改到位的地方一共 9 处，全部是「怎么汇总」，没有一处改登记数据：

1. 账户余额（`_calc_account_balance` / `_recalc_all_account_balances`）；
2. 未来日期余额快照里的账户段；
3. 「添加账户结余」时算当天结余；
4. 「账户结余」页的收入 / 支出两列；
5. 列表里的「账户」列（还款显示成它真正还的那个账户，不再是空白或错账户）；
6. 按账户筛选（选哪个账户，还款跟着它借的那笔借款走）；
7. CSV 导出的账户列；
8. Excel 导出的账户列；
9. 删除账户前的引用检查（不会再有「还款挂在别的账户、却属于本账户借款」被漏查，删完留孤儿）。

另外**启动自愈多了一步**：程序打开用户库时，会把所有历史「余额」快照从 `0000-01-01` 起全量重算一遍。所以**库复制进去、打开程序，该算对的就都对了**，不需要手动修库、也不用重录任何记录。旧库已经存着的错误快照（比如某天存成 -1016.46）会在这一步被覆盖成正确值。

**唯一没改的一处**：`upgrade_database_schema()` 里反推 `initial_balance` 那段仍按原始 `account_id` 算 —— 那里是在还原「你当初填的初始余额」= 当时余额 − 当时净额，两边必须用同一口径才还原得准；换成 EFF 反而会把历史误差永久写进初始余额。

自查工具：`_scaffold\_probe_eff_v75.py`（27 项）。它先把两个真实库**逐条**比对一遍，证明登记数据一条都没变（条数、类型、金额、日期、账户、关联借款），再验证 9 个汇总口径全对。

**v7.6**：**记录多了，不再一屏几百行地往下拖。**

以前主列表把所有记录一次性画出来，几百条还能忍，上千条就很难找人。这一版把列表**分成页**显示：

- 表格下面多了一条**分页条**：首页 / 上一页 / 下一页 / 末页 四个按钮，中间写着「**第 3 / 9 页（共 861 条，本页 201-300 条）**」，最右边是「每页行数」下拉框。
- **默认每页 100 行**，可选 20 / 50 / 100 / 200 / 500。选完立刻生效并**自动记住**，下次打开还是这个行数。
- **关程序时会记住你看到哪一行**，下次打开自动回到那一页，滚动条也放回原来的位置 —— 不用再自己翻回去找。
- **分页只是「怎么显示」，不是「怎么算」**：查询还是一次把结果全取回来，统计、账户余额、余额快照、导出、筛选全都按全量算，一点都不受影响。这一点有专门的探针 `_probe_page_v76.py` 反复翻页后核对余额与合计来证明。
- **一改筛选条件就自动回第 1 页**：否则你停在第 5 页，筛选后只剩 3 条，表格会一片空白，看着像「一条都没查到」。
- 设置里多了「**列表显示**」一栏：
  - **每页行数**：20 / 50 / 100 / 200 / 500；
  - **列表「日期」列显示时分秒**：默认开。要截图发人时**临时关掉**就只剩纯日期（`2026-11-21`），库里的时间**一个字节都不动**，再打开立刻恢复。
- 顺带修掉 v7.5 留下的一个崩溃：v7.5 把账户名改成了标量子查询，但搜索条件里还留着一句 `a.name LIKE ?`，**一输入搜索词就报 `no such column: a.name`**。现在搜索账户名也走同一口径，输入框随便打字都不会崩。

自查工具：`_scaffold\_probe_page_v76.py`（30 项）。七段断言里最要紧的是 B 段：在翻页前后各取一次「账户余额 / 快照条数与合计 / 借款还款合计」，三次完全一致 → 证明分页没有参与任何计算。

## 第五部分：核心功能逐项详解（带大量举例）

### 5.1 记账：收入 / 支出

**场景**：小李今天发工资 8000 元。

1. 点"添加记录"。
2. 类型选"收入"。
3. 金额填 `8000`。
4. 类别选"工资"。
5. 日期默认今天，右边的**时间框**默认当前时刻（★v7.2 新增，v7.3 起秒为 2 位；不改就是现在，改了就是那笔钱实际到账的时刻）。
6. 描述填"9月工资"。
7. 账户选"招商银行卡"。
8. 点确定。

**结果**：交易记录里多一条，类型显示"收入"（绿底），金额 8000.00。账户"招商银行卡"余额 +8000。

**场景**：小李中午吃饭花了 35 元。

1. 点"添加记录"。
2. 类型"支出"，金额 `35`，类别"餐饮"，描述"公司楼下快餐"。
3. 账户"支付宝"。
4. 确定。

### 5.2 借款与还款

**场景**：小王借给朋友 5000 元，朋友分两次还：先还 2000，再还 3000。

**第一步：记借款**

1. 添加记录 → 类型"借款" → 金额 `5000` → 描述"借给张三" → 账户"招商银行卡"。
2. 保存后，这条记录状态是"待还款"，表格里显示"借款 (剩余:5000.00)"。

**第二步：第一次还款**

1. 添加记录 → 类型"还款" → 金额 `2000`。
2. **关联借款**下拉框会列出所有待还款借款，选"ID:1 金额:5000 ..."。
3. 保存。

**结果**：借款状态仍是"待还款"，剩余变成 3000.00。

**第三步：第二次还款**

1. 添加记录 → 类型"还款" → 金额 `3000` → 关联同一笔借款。
2. 保存。

**结果**：系统发现还款总额 2000+3000=5000，等于借款金额，自动把借款状态改成"已结清"（绿底），剩余显示消失。

**超额还款场景**：朋友还了 6000（多还 1000）。

- 系统弹窗问："还款金额超过剩余应还金额 5000.00 元，是否将超额部分(1000.00元)记录为收入?"
- 选"是"：5000 记为还款，1000 记为收入（类别"退款"，描述"借款ID:1还款超额退款"）。
- 选"否"：取消，不记录。

#### 5.2.1 一键还款 / 一键批量还款（★ v6.6 / v6.7，v6.9 修正落账户，v7.0 修按钮误显）

手工填剩余金额太麻烦，程序给了两个快捷入口。**两者填的都是「剩余应还」，不是原始借款全额**。

**入口一：弹窗里的「一键还款」按钮（v6.6）**

1. 添加记录 → 类型选「还款」；
2. 金额框左边会多出一个 **「一键还款」** 按钮，点它；
3. 程序自动取第一笔待还借款的剩余金额填进金额框，并直接点确定——不用手算、不用再点保存。

**入口二：主界面工具栏的「一键批量还款」（v6.7）**

1. 点工具栏「一键批量还款」；
2. 弹窗列出所有 `待还款` 的借款，每行可勾选；顶部有「全选 / 全不选」；
3. 点确定，程序逐笔按剩余金额生成还款记录并把借款标记为已结清；
4. 状态栏会提示「✅ 已批量还款 N 笔借款!」。

**★ v6.9 修正的关键点：还款记到哪个账户？**

| 版本 | 一键还款记到 | 后果 |
| --- | --- | --- |
| v6.6 / v6.7 / v6.8 | 弹窗当前选中的账户；批量还款直接写 `-1` | 借款从账户 A 扣掉、还款却没回到 A，**A 永久偏负**；批量还款还完全不重算 |
| **v6.9 起** | **借款记录所在的那个账户**（`get_account_id_for_loan`） | 借出多少、回来多少，账户余额自动闭合 |

举例：借款记在「招商银行卡」，你在弹窗里当前选的是「现金账户」，v6.8 会把还款记到「现金账户」（错），v6.9 会记到「招商银行卡」（对）。
**★ v7.0 修掉的坑：按钮该藏没藏，点出来存错类型**

以前这个「一键还款」按钮**在任何类型下都看得见**（Qt 把它加进按钮栏时会自己 `show()`，把之前的隐藏设置顶掉）。你点它时如果类型还停在「账户结余」或「收入」，程序就照那个类型存了一条快照/收入，看着就像「一键还款存成账户结余」。

v7.0 起：

- 只有类型选「还款」，这个按钮才出现；
- 就算在别的类型下点到（老版本遗留、或键盘操作），程序也会**先把类型切成「还款」**，切不过去就提示「请先把类型选为『还款』」并中止；
- 弹窗打开时不再记忆「余额 / 账户结余 / 待还款合计」这三种一次性类型。

> 想核对自己的还款有没有记错账户：跑 [5.3.3 对账自检](#533-对账自检怀疑数字不对时先跑这个) 的 C 条 SQL，返回 0 才正常。

### 5.3 余额 / 账户结余 / 待还款合计

这三个是**自动计算**的特殊类型：

| 类型 | 算什么 | 例子 |
| --- | --- | --- |
| 余额 | 所有账户的总余额（截至某日期） | 截至 2026-09-19 总余额 |
| 账户结余 | 某个账户的余额 | 招商银行卡截至今天的余额 |
| 待还款合计 | 所有待还款借款的剩余总额 | 现在总共还欠别人多少 |

**注意**：选这三种类型时，金额输入框会被**禁用**，因为系统自动算。

#### 5.3.1 余额到底怎么算的（★ v6.9 起唯一公式）

> **`账户余额 = 初始余额(initial_balance) + 该账户流水净额`**
>
> **`总余额 = 所有账户的初始余额之和 + 全库流水净额`**
>
> 流水净额 = `收入 − 支出 + 还款 − 借款`（`type` 为 `income` / `expense` / `还款` / `借款` 四种，其余类型一律不参与）。

这个公式在代码里**只有一处定义**（`Finance_App.py` 的 `_NET_FLOW_SQL` 常量），所有增删改操作最后都汇到同一个收尾入口 `refresh_after_change()`，不再各写各的。

**为什么要单独存一个「初始余额」？**

旧版本（v6.8 及以前）把你在「编辑 → 管理账户」里填的初始金额**直接写进 `balance` 字段**，而每次重算又会用流水净额**覆盖** `balance`。结果是：

- 你新建账户时填「初始余额 1000」，界面上确实显示 1000；
- 但只要一记账（哪怕只记一笔 1 元支出），重算就把它覆盖成「流水净额 = −1」，那 1000 元凭空蒸发；
- 手工改成正确的数，下次重算再抹一次。

v6.9 起初始余额单独存 `accounts.initial_balance`，重算只算流水、再加上初始值，**初始余额绝不被覆盖**。升级时会自动迁移：对每个账户按 `initial_balance = 当前 balance − 该账户流水净额` 回填，所以**升级那一刻你看到的余额一分不会变**。

#### 5.3.2 哪些操作会触发重算

下面每一条改完都会走 `refresh_after_change()`，一次把「账户余额 → 未来日期余额快照 → 账户结余汇总 → 列表 → 借款下拉 → 统计 → 账户表」全部刷新：

| 操作 | v6.9 之前 | v6.9 之后 |
| --- | --- | --- |
| 添加记录（收入/支出/借款/还款） | 只刷当前账户 | 全量对账 |
| **一键还款**（弹窗内按钮） | 记到「表单当前账户」，可能不是借款账户 | 记到**借款所在的账户** |
| **一键批量还款**（主界面按钮） | 写 `account_id = -1`（不存在的账户），**完全不重算** | 逐笔记到各自借款账户，并全量对账 |
| 编辑记录（含改金额 / 改账户 / 改日期） | 只重算**新**账户，旧账户留着旧值 | 新老账户都重算 |
| 删除记录 | 逐账户重算 | 全量对账 |
| 标记已结算 | 只改状态、**不写还款记录**，一刷新就自动变回未结算 | 补写真实还款记录后再标记 |
| 超额还款调整 | 改完不刷新 | 全量对账 |
| 定期交易执行 / 删除 | 执行时**篡改历史记录的日期**，且不刷新 | 保留历史日期、另存下次执行日，并全量对账 |
| 撤销上一步 | 不刷新余额 | 全量对账 |
| 程序启动 / 切换用户 | 只对有状态变化的借款账户重算 | **启动自愈**：按公式对齐一次全部账户 |
| 添加「待还款合计」（主界面 / 弹窗） | 只刷列表 | **★v7.4** 全量对账 |
| 新增账户 / 编辑账户初始余额 / 删除账户 | 只刷账户表，余额快照不跟着变 | **★v7.4** 全量对账（初始余额变了，总快照必须重算） |
| 从备份恢复数据 | 只刷列表 + 统计 | **★v7.4** 全量对账 |
| **某账户的余额 / 账户结余，和全库净额对不上**（典型：全库 0.00，账户 -1016.46） | 早年「一键批量还款」把还款的 `account_id` 写成 `-1`，这条钱没算进任何账户 | **★v7.5** 全部改成按「有效账户归属」汇总：还款跟着它偿还的那笔借款走；启动时还会把历史快照全量重算一遍。登记数据不动 |
| 翻页 / 改每页行数 / 开关「显示时分秒」（★v7.6） | 没有分页，几千条一次画完，卡且找不到人 | **纯显示层**：只改变当前这一页画哪些行，**不触发任何重算、不写库**；关程序记住看到的行号，下次自动回到原处 |

#### 5.3.3 对账自检（怀疑数字不对时先跑这个）

用任意 SQLite 工具打开 `finance_<用户名>.db`，跑下面三条，**必须全部成立**：

```sql
-- A. 每个账户：balance 应等于 initial_balance + 该账户流水净额
SELECT a.id, a.name, a.balance,
       IFNULL(a.initial_balance,0) + IFNULL((
         SELECT SUM(CASE type
                      WHEN 'income'  THEN amount
                      WHEN '还款'    THEN amount
                      WHEN 'expense' THEN -amount
                      WHEN '借款'    THEN -amount
                      ELSE 0 END)
         FROM transactions t
         WHERE t.account_id = a.id
           AND t.type IN ('income','expense','借款','还款')
       ),0) AS should_be
FROM accounts a;   -- balance 与 should_be 必须逐行相等

-- B. 总账：所有账户余额之和 == 所有初始余额之和 + 全库流水净额
SELECT (SELECT SUM(IFNULL(balance,0))         FROM accounts) AS sum_balance,
       (SELECT SUM(IFNULL(initial_balance,0)) FROM accounts) AS sum_initial,
       (SELECT IFNULL(SUM(CASE type
                      WHEN 'income'  THEN amount
                      WHEN '还款'    THEN amount
                      WHEN 'expense' THEN -amount
                      WHEN '借款'    THEN -amount
                      ELSE 0 END),0)
        FROM transactions
        WHERE type IN ('income','expense','借款','还款')) AS net_flow;
-- 期望：sum_balance == sum_initial + net_flow

-- C. 有问题的还款记录（正常应 0 行）
SELECT COUNT(*) FROM transactions
WHERE type = '还款' AND (account_id IS NULL OR account_id <= 0);
```

三条里任意一条不成立，先跑 `_scaffold\audit_all_dbs.py`（只读体检，不写库）定位是哪个库、哪个账户。

#### 5.3.4 「待还款合计」不会重复计算

「待还款合计」= 对每笔 `type='借款'` 且 `status='pending'` 的记录，取 `max(0, amount − 该借款名下已还金额)` 再求和。它**不参与**余额公式（该 `type` 不在那四种里，会被 `CASE` 天然排除），所以记一笔「待还款合计」快照**不会改变任何账户余额**，只作为当天的「欠款快照」留档。

### 5.4 多账户管理

**场景**：老张有现金、招行卡、支付宝、微信四个账户。

1. 编辑 → 管理账户 → 添加。
2. 分别添加：
   - 现金账户，初始 500，CNY
   - 招商银行卡，初始 20000，CNY
   - 支付宝，初始 3000，CNY
   - 微信钱包，初始 1000，CNY

之后记账时，账户下拉框能选这四个。账户结余页能看到每个账户的余额。

**多币种**：账户可以设 USD、EUR、JPY 等，配合"工具 → 汇率转换"使用。

#### 5.4.1 「类型」和「账户」会被记住（★ v7.1）

**它记什么**：上次在「添加记录」里选的**类型**（收入/支出/借款/还款）、**账户**、**类别**。下次打开，直接就是上次那三个。

**它记在哪**：当前用户库 `settings` 表的三组键 —— `last_type`、`last_account` + `last_account_id`、`last_category`。**每次你改动下拉框，立刻落盘**，不依赖点确定、也不依赖正常退出（任务管理器强杀也不丢）。

**账户为什么存两份**：`last_account` 存名字，`last_account_id` 存编号。恢复时**先按编号找**，找不到才按名字找。所以你给账户改名（「银行2」→「招商银行」）之后，下次打开仍然是它，不会因为旧名字找不到而退回第一个账户。

**三种类型不记**：「余额」「账户结余」「待还款合计」是**一次性快照**类型（金额框被禁用，点确定就写一条快照记录）。这三个不参与记忆，下次打开一律回到四个日常类型之一 —— 这是 v7.0 为避免误存刻意做的。

**切换用户互不干扰**：每个用户的记忆存在自己的库里。A 用户记「支出 + 招商银行」，B 用户记「收入 + 支付宝」，切来切去各记各的。

**想让它回到默认**：随便把下拉框改一次就行（改动立即成为新的记忆）；想彻底清掉，删掉该用户库里 `settings` 表这三行即可。

**常见困惑**：

| 现象 | 说明 |
| --- | --- |
| 我在主界面选了「借款」，弹窗打开也是「借款」 | 正常，两处共用同一份记忆（★ v7.1） |
| 上次选的是「账户结余」，这次打开变成「收入」 | 正常，快照类型不记忆（v7.0 起） |
| 我把账户改名了，下次还是新名字 | 正常，按编号记的（★ v7.1） |
| 换了个用户，选择变了 | 正常，各用户各自记忆（★ v7.1） |

- 支出：餐饮、购物、娱乐、交通、住房、医疗、教育、其他

### 5.6 预算管理

**场景**：小李想控制每月餐饮支出不超过 1500 元。

2. 选择月份（默认当前月）。

### 5.10 搜索与筛选

**拼音搜索原理**：程序用 `pypinyin` 库把中文转成拼音首字母。比如"餐饮"→`cy`。你输入 `cy`，程序会：
1. 先直接 LIKE 匹配描述、金额、分类、标签、账户名。
2. 再把数据库里所有描述和分类转成拼音首字母，看哪些以 `cy` 开头。
3. 合并结果。

**组合筛选举例**：
- 类型"支出" + 分类"餐饮" + 时间范围"最近一月" → 看最近一月的餐饮支出。
- 状态"待还款" + 账户"招商银行卡" → 看招行卡上还没还的借款。

### 5.10.1 日期与时间（★ v7.2 新增，v7.3 秒改 2 位）

**每条记录现在带时分秒**。列表「日期」列显示成 `2026-11-21 16:31:06`：

```
2026-11-21 16:31:06
└────┬───┘ └───┬───┘
     日期      时间
              └─ 时:分:秒（各 2 位，共 8 位）
```

时间的格式是标准 24 小时制 `HH:MM:SS`，**永远是 8 位**（`09:05:03`、`00:00:00` 都补齐前导零）。v7.2 曾按最初需求把秒写成 4 位（`16:31:0600`），v7.3 已按你的要求改回 2 位。

| 场景 | 怎么填 / 自动变成什么 |
| --- | --- |
| 手动添加 | 「日期」旁边有时间框，默认当前时刻，可手改成任意 `时:分:秒`，秒精确到整秒 |
| 编辑已有记录 | 双击那行 → 对话框里日期旁同样有时间框，改完确定即生效 |
| 粘贴交易提醒 | 提醒里写 `16:31:06` → 存成 `16:31:06`；只写 `16:31` → 存成 `16:31:00`；没写时间 → 存成 `00:00:00` |
| 一键还款 / 批量还款 / 标记已结算 / 超额调整 | 自动取**操作当下**的时间 |
| 定期交易自动生成 | 沿用模板那条记录的时间 |
| 老数据（v7.2 之前录的） | 统一是 `00:00:00`，即「那天 0 点」，**不影响任何统计** |

**同一天内的排序**：以前只能按录入顺序（id），现在按时间先后 —— 08:00 那条排在 16:31 那条前面。

**为什么时间不塞进「日期」那一列？**（技术原因，不看也行）

SQLite 只认到秒。把 `2026-11-21 16:31:06` 塞进日期列，它当**非法时间**处理，`strftime('%Y-%m', date)` 直接返回 `NULL` —— 全项目所有**按月统计会静默变成 0，一个错误提示都不会有**；日期区间筛选也会用 `BETWEEN ... AND '2026-11-21'` 把当天记录全部挡掉。所以内部是**两列**：`date` 永远纯 `2026-11-21`，`rec_time` 存 `16:31:06`，只在**显示和导出时**拼起来。这样 30 多处统计 SQL 一行都没改。

> v7.3 起展示层还会再过一遍 `rec_time_normalize()`：库里万一残留 v7.2 的 10 位老值（`16:31:0600`），界面也只显示 8 位。

**老数据体检 / 补时间**：

```bash
cd /d G:\Python_Code\Finance_App
python _scaffold\audit_rec_time.py            # 只读演练，看哪些库要补
python _scaffold\audit_rec_time.py --apply    # 真写（写前自动把整库备份到 backups\）
```

本机 18 个库共 4427 条老记录，已统一补成 `00:00:00`；v7.3 又把其中 v7.2 写下的 10 位值全部裁成 8 位（复跑 dry-run 结果「0 个库需要处理」）。

## 第六部分：交易提醒自动填写——最实用的功能

### 6.1 为什么需要它？

你每天收到银行短信/微信提醒，格式大概是这样：

```
您尾号1234的储蓄卡9月18日14:30消费人民币12.34元，账户余额1,234.56元。
```

以前要手动抄：金额 12.34、商户（没有）、日期 2026-09-18 14:30、类型支出。现在**整段粘贴**，点一下，全自动填好。

### 6.2 支持的格式

**格式 A：微信/短信一行式**

```
您尾号1234的储蓄卡9月18日14:30消费人民币12.34元，账户余额1,234.56元。
```

**格式 B：银行 App 分行式**（标签 + 空格 + 值）

```
交易提醒
交易时间    2026年09月17日 22:58
交易类型    尾号1234的储蓄卡，存入
交易金额    人民币200.00
账户余额    人民币928.5
交易附言    存银行
```

**格式 C：支付宝**

```
支付宝-肯德基（中关村店）
交易金额：88.00元
交易时间：2026-09-18 12:30
```

### 6.3 怎么用？

1. 点"添加记录"。
2. 在"标签"字段下方，找到"交易提醒信息"分组框。
3. 把提醒文本**粘贴**到文本框里。
4. **两种触发方式**：
   - 粘贴后等 350 毫秒，自动解析（防抖）。
   - 或者点"🔍 解析并填写"按钮。
5. 状态标签显示"✅ 已自动填写：类型=支出、金额=12.34、描述=肯德基、日期=2026-09-18 12:30"。
6. 检查一下，点确定。

### 6.4 识别规则详解

#### 金额识别（优先级从高到低）

1. **标签紧邻**：`交易金额：88.00` / `交易金额    人民币200.00`
2. **关键词附近**：`支出人民币12.34元` / `12.34元消费`
3. **带币种符号**：`¥88.00` / `￥88` / `RMB 88`
4. **带"元"**：`88元`
5. **其它小数**：`88.00`

**自动排除余额**：`账户余额1,234.56元` 里的 1234.56 **不会**被当交易金额，因为前面有"余额"。

**支持千分位**：`1,234.56` → 1234.56。

**支持万元/千元**：`1.5万元` → 15000。

#### 商户识别

**标签优先**：`交易商户：肯德基` / `商户名称    肯德基` / `收款方：张三` / `对方户名-张三`

**句式兜底**：
- `向肯德基付款` → 肯德基
- `支付给张三` → 张三
- `支付宝-肯德基（中关村店）` → 肯德基（中关村店）

**清洗规则**：按标点 `，,。；;、|` 截断、上限 30 字、去成对括号（但保留商户名内的括号）。

#### 交易附言（没有商户时用）

**标签**：交易附言 / 附言 / 交易摘要 / 摘要 / 交易备注 / 备注 / 交易说明 / 用途 / 说明 / 订单标题

**关键**（★ v4.7）：附言是**自由文本**，**不按逗号截断**，上限 100 字。

**举例**：
- `交易附言 银联无卡转账,对手户名-张三` → 完整保留"银联无卡转账,对手户名-张三"
- `交易附言 银联无卡转账,对手户名-张三 账户余额 人民币728.5` → 只取"银联无卡转账,对手户名-张三"（"账户余额"是下一个字段，切掉）

#### 日期时间识别

- 含年：`2026-09-18 14:30` / `2026年9月18日`
- 不含年：`9月18日` / `09-18`
- 相对：`今天` / `昨天` / `前天`
- 仅时间：用今天
- 时间格式：`14:30` / `14时30分` / `14点` / `下午3:05`

**跨年处理**：不含年且日期落在未来，按去年处理。

#### 收支方向识别

**强特征词**（优先）：
- 支出：支出、消费、付款、转出、扣款、取现、取款、支取、缴费、代扣、还款
- 收入：收入、入账、转入、存入、退款、冲正、工资、报销、利息、红包、汇入、到账、收益

**弱特征词**（无强特征词时）：
- 支出：支付、购买、扣费、汇出
- 收入：存款、退货

**特别注意**：弱词"支付"会跳过"支付宝/支付方式/支付成功"等品牌或状态词。所以"微信支付收款到账"会判成**收入**，不是支出。

## 第七部分：设置与持久化——为什么你的选择会被记住

### 7.1 设置存在哪？

每个用户的数据库 `finance_<用户名>.db` 里有一张 `settings` 表：

```sql
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT
)
```

主库 `finance_master.db` 的 `settings` 表只存 `last_user`。

### 7.2 已持久化的键

| 键 | 含义 | 何时保存 |
| --- | --- | --- |
| `date_range` | 时间范围下拉框索引 | 变更时 |
| `last_type` | 最后选的类型 | 变更时 |
| `last_account` | 最后选的账户 | 变更时 |
| `last_category` | 最后选的类别 | 变更时 |
| `max_backups` | 最大备份数 | 变更时 |
| `backup_interval_hours` | 备份间隔小时 | 变更时 |
| `window_geometry` | 窗口几何（base64） | 拖动停止 800ms 后 |
| `window_maximized` | 是否最大化 | 同上 |
| `scroll_bottom_after_add` | 添加后是否滚到底（★ v4.9） | 点选即存 |
| `page_size` | 每页显示多少行（★ v7.6，默认 100） | 点选即存 |
| `show_time_in_list` | 列表「日期」列是否显示时分秒（★ v7.6，默认 1） | 点选即存 |
| `list_anchor` | 上次看到的那一行（全局行号，★ v7.6 用来恢复页码） | 翻页/滚动停止 800ms 后 |
| `list_scroll` | 上次的页内滚动位置（★ v7.6） | 同上 |

### 7.3 窗口几何实时保存（★ v4.4 / v4.5）

**三个入口**：
- `resizeEvent`：尺寸变
- `moveEvent`：位置变
- `changeEvent(WindowStateChange)`：最大化/还原

**流程**：
```
事件 → _schedule_geometry_save() → 800ms 防抖 → _save_window_geometry()
```

**不写的条件**：
- `_geom_restoring=True`（启动恢复期间）
- 窗口不可见
- 窗口最小化

**为什么要有防抖？** 拖动窗口时 `resizeEvent` 会触发几十次，每次都写库太慢。防抖 800ms 意味着你停手 800ms 后才写一次。

### 7.4 ★ v4.5 修复的 Bug（重要）

**现象**：窗口尺寸改了记不住。

**根因**：`load_settings()` 中间步骤 `update_date_range()` 末尾会调 `save_settings()`，而那时窗口还是默认尺寸 `resize(1200,800)`，默认尺寸被写进库。恢复几何的代码在函数最后才读库，读到的是刚写进去的默认值。

**修复**：
1. `load_settings()` **开头**先把 `window_geometry` / `window_maximized` 读到局部变量。
2. `save_settings()` 在 `_geom_restoring=True` 时**跳过**写这两个键。
3. `GEOMETRY_SAVE_DELAY_MS` / `_geom_restoring` / `_geom_save_timer` 默认值放**类级**，不用 `getattr(self, '不存在的属性', 默认)`——sip 对象上取不存在的属性会抛 `RuntimeError`。

**这三条在未来重构时必须保留。**

### 7.5 设置对话框（★ v4.9）

**打开方式**：工具 → 设置…

**特点**：
- 选项**点选即保存**，没有"保存"按钮，只有"关闭"。
- 复选框状态一变，立即回调 `_on_setting_changed(key, value)`，主窗口立即应用 + 写库。

**现有选项**：
- "添加记录后自动滚动到列表底部"（`scroll_bottom_after_add`）

**实现细节**：
- 对话框类 `SettingsDialog`，构造参数 `(parent, values, on_change)`。
- **先 `setChecked` 再连信号**，否则构造时会用默认值误触发一次"变化"。
- `load_settings` 里必须**先把新键读出来**（放在开头、`date_range` 之前），否则中间的 `update_date_range()` 会调 `save_settings()`，新键被类级默认值盖掉。

**新增选项的步骤**：
1. `_build_ui` 加控件 + `_bind_bool(控件, "键名")`。
2. `load_settings` 读、`save_settings` 写。
3. 类级默认值。
4. `_on_setting_changed` 里加分支应用。

## 第八部分：数据安全——备份、加密、撤销

### 8.1 备份

**手动备份**：文件 → 备份与恢复 → 手动备份。

**自动备份**：默认每小时一次。可设间隔（每小时/每天/每周/每月）和最大份数（默认 30）。

**备份文件命名**：`finance_<用户名>_<类型>_<YYYYMMDD>.db`
- 类型：auto / manual / before_restore

**清理**：超过 `max_backups` 份时，删最旧的。

**恢复**：
1. 文件 → 备份与恢复 → 恢复备份。
2. 弹出对话框，列出所有备份（时间、类型、大小、数据库版本）。
3. 可以按类型/日期筛选。
4. 勾选一个，点确定。
5. 恢复前会先自动备份当前数据（`before_restore`）。

### 8.2 加密

**加密**：
1. 文件 → 加密数据库。
2. 输入密码。
3. 程序用 PBKDF2（SHA256，100000 次迭代，固定 salt `b'some_salt'`）从密码派生密钥，再用 Fernet 加密整个数据库。
4. 密码存进主库 `users.password`。

**加密后**：
- 数据库文件变成密文，别人拿到也打不开。
- 程序运行时解密到内存（`:memory:`），操作内存库。
- 退出时把内存库导出、加密、写回文件。

**解密**：
1. 文件 → 解密数据库。
2. 输入密码。
3. 验证通过后，把明文写回文件，清空 `users.password`。

**注意**：加密用的是**固定 salt**，实际生产环境应该每用户唯一 salt。这是已知的安全简化。

**★★ v6.9 修复的一个致命 Bug（务必升级）**

v6.8 及以前，「加密数据库 / 解密数据库 / 切换用户 / 退出 / 备份」这几个动作导出数据时，代码走的是：

```python
temp_conn = sqlite3.connect(':memory:')   # ← 新建一个**空**内存库
dump = temp_conn.iterdump()              # ← 导出的是空库，只有一个换行
```

也就是说它**从来没有真正读过 `self.conn`**，导出结果恒为空。后果有三个，都是数据级事故：

| 场景 | v6.8 及以前的行为 | v6.9 起 |
| --- | --- | --- |
| 加密模式下**撤销**（Ctrl+Z） | 用空 dump 覆盖当前库 → **整库被清空** | 恢复正常 |
| 加密模式下**切换用户 / 退出** | 写回的是空库 → **数据全丢** | 恢复正常 |
| 加密模式下**备份** | 备份文件是空壳，真出事恢复不回来 | 恢复正常 |

v6.9 改成直接用 `self.conn.iterdump()`（同一个连接、真实数据），并在代码里加了「`temp_conn` 就是 `self.conn`，绝不能 close」的注释防止后人改回去。

**如果你在 v6.8 及以前用过加密模式**：请立刻检查 `backups\` 里的加密备份文件大小——如果只有几百字节，那些备份是无效的，不要指望能恢复。同时确认当前数据是否完整（打开后记录条数对不对），必要时用 `backups\` 里 `auto` 类型的**未加密**备份恢复。

### 8.3 撤销

**原理**：每次 `save_state_before_change()` 把当前数据库复制一份到 `temp_undo_*.db`，压栈（最多 10 个）。

**触发**：Ctrl+Z 或 编辑 → 撤销。

**限制**：
- 撤销栈在内存里，程序关闭就没了（最多 10 步）。
- 临时文件每 6 小时清理一次（超 24 小时的删）。
- 加密库的撤销文件也是加密的。

**★ v6.9 起撤销之后会重算余额**：以前撤销只把数据换回去、界面数字还是旧的，必须手动关掉重开才对。现在撤销完会走统一收尾 `refresh_after_change()`，账户余额、余额快照、账户结余页、统计图一次性全部对齐。

**⚠ 加密模式下撤销曾经是致命操作**，v6.9 已修，详见 [8.2 加密](#82-加密) 里的「★★ v6.9 修复的一个致命 Bug」。

### 8.4 数据隔离

**多用户**：每个用户独立数据库 `finance_<用户名>.db`。切换用户时关闭当前库、打开新库。

**主库**：`finance_master.db` 只存用户列表和 `last_user`。

## 第十二部分：故障排查手册

### 12.1 程序打不开

**症状**：双击 exe 没反应，或闪一下就没了。

**排查**：
1. 看是不是把 exe 单独拎出来了——它需要同目录的 `icon.ico` 等文件。
2. 如果是源码运行，看命令行报什么错。
3. 检查 Python 版本是不是 3.10。
4. 检查依赖是否装齐。

### 12.2 窗口尺寸记不住

**排查**：
1. 确认版本 ≥ 4.5（4.4 有 Bug）。
2. 检查数据库 `settings` 表里有没有 `window_geometry` 键。
3. 如果是加密库，检查退出时是否正确写盘。

### 12.3 交易提醒解析不出来

**排查**：
1. 看提醒文本里有没有金额、日期。
2. 金额是不是被"余额"上下文排除了。
3. 试试手动点"🔍 解析并填写"。
4. 看状态标签提示什么。
5. 如果格式特殊，可能需要扩展识别规则（见 6.6）。

### 12.4 交易附言缺后面一段

**排查**：
1. 确认版本 ≥ 4.7。
2. 4.7 之前附言用商户清洗器，会在逗号处截断。
3. 升级到 4.7+ 即可。

### 12.5 筛选栏窗口太宽

**排查**：
1. 确认版本 ≥ 4.8。
2. 4.3 之前筛选栏最小宽度 1400+，4.3 降到 735，4.8 是 792。
3. 如果还是宽，可能是窗口几何存的是旧值，手动拖窄一次。

### 12.6 新增记录看不到

**排查**：
1. 确认版本 ≥ 4.6。
2. 4.6 之前时间范围锚定选择那一刻，程序开着过夜就会出问题。
3. 点"重置"或切到"全部时间"看看。

### 12.7 数据库打不开

**排查**：
1. 是不是加密库？需要密码。
2. 用 SQLite 工具打开，看文件头是不是 `SQLite format 3`。
3. 如果是密文，需要先解密。

### 12.8 编译后 exe 不是最新代码

**排查**：
Nuitka 在**编译开始时**读源码，编译要几分钟。如果编译启动后又改了源码，产物是旧的。

**验证方法**（★ v6.9 改：不要再用裸 `python -c` 拼正则，Windows 上引号转义极易出错）：

直接用项目自带的验证脚本：

```powershell
Push-Location "G:\Python_Code\Finance_App"
& "D:/Program Files/Python310/python.exe" -u _scaffold/verify_exe.py
Pop-Location
```

它会打印源码里的最新版本号，并逐项检查：

1. **源码最新那条 `VERSION_HISTORY` 明文是否出现在 exe 字节里** —— 这是判断「exe 是不是最新代码」的唯一可靠依据（Nuitka 只要编译期间改了源码，产物就是旧的，但日志照样报 `Successfully created`、退出码 0）；
2. dist 目录里 PySide6 的关键 DLL / 插件是否齐全；
3. exe 里有没有 PyQt5 残留特征串（v6.0 迁移后应当只剩历史说明文本）；
4. `icon.ico` 是否在 exe 旁边（运行时 `QIcon("icon.ico")` 读的是同目录文件，不是打包进 exe）。

全部 ✅ 才算最新。出现 ❌ 就重新编译。

### 12.9 余额 / 账户结余和我想的不一样 / 一键还款存错类型 / 选择记不住 / 时间显示不对 / 数字变两次 / 账户加总对不上全库 / 记录太多翻不到 / 截图上带着时间（★ v6.9 新增，v7.0、v7.1、v7.2、v7.3、v7.4、v7.5、v7.6 补）

**先分清是哪一类对不上**，不同症状对应不同原因：

| 症状 | 最可能的原因 | 怎么办 |
| --- | --- | --- |
| 账户余额比实际少了一笔借款的钱（偏负） | v6.8 及以前「一键批量还款」把还款记到 `account_id = -1`，钱没回到账户 | 升级到 v6.9 后跑一次 `_scaffold\fix_legacy_account_id.py`（先不加 `--apply` 演练，看结果对不对再加） |
| 新建账户时填的初始余额，一记账就变成 0 / 负数 | v6.8 及以前把初始余额写进 `balance`，被下一次重算覆盖 | 升级到 v6.9 会自动迁移回填 `initial_balance`；若已被覆盖，在「编辑 → 管理账户 → 编辑」把余额重新填一次 |
| 「余额统计」页的总数比账户表合计少一截 | v6.8 及以前快照只算流水、没算初始余额 | v6.9 已修，重新添加一条「余额」记录即对齐 |
| 改了某笔记录的账户，旧账户余额还留着旧数 | v6.8 及以前编辑只重算新账户 | v6.9 已修（新老账户都重算） |
| 删了记录余额没变 | v6.8 及以前少数删除路径只刷列表 | v6.9 已修（统一走 `refresh_after_change()`） |
| 账户余额凭空多出/少了某个数 | 可能有 `account_id` 为 NULL 的历史记录只进了总账 | 跑 5.3.3 的 C 条 SQL 查出来，再用「编辑」补上账户 |
| **明明点的是「一键还款」，列表里却多出一条「账户结余」/「收入」** | v6.9 及以前的 Bug：`QDialogButtonBox.addButton()` 会主动 `show()` 那个按钮，把 `setVisible(False)` 顶掉 —— 于是「一键还款」在任何类型下都可见，点它时类型还是上次留下的，程序把当前类型原样提交了 | 升级到 v7.0。已生成的那条错记录：到列表里找到它（类型是「账户结余」或「收入」、描述是「截至 X 的账户结余」或金额刚好等于剩余应还），**右键删除**即可；若它已经影响了余额，删掉后 v7.0 会自动重算对齐 |
| **「类型」/「账户」记住一次，重启就忘（账户总是回到现金账户）** | v7.0 及以前的 Bug：`create_input_form()` 里的 `update_form()` 会把账户下拉框切到第一个真实账户，这个中间态触发 `currentIndexChanged` → `save_last_account()` **当场把默认值写进库**，等真正的 `load_settings()` 再读时已被覆盖（类型没这问题，因为它的赋值在监听建立之前） | 升级到 v7.1。已存在的错误记忆不用管，升级后第一次选好就会重新记对 |
| **日期后面多了一串时间，看着别扭 / 显示成 `2026-11-21 00:00:00`** | v7.2 起每条记录都有 `rec_time`，老数据统一补 `00:00:00`（那天 0 点），这是正常值不是错误 | 想要准确时间就双击那条记录，在日期旁边的时间框里改；不想看时间只是纯审美问题，不影响任何统计 |
| **看到秒是 4 位（`16:31:0600`）/ 升级后还是 4 位** | v7.2 的写法是 4 位秒，v7.3 已改回 2 位。若仍看到 4 位，说明程序还是 7.2，或该库没被裁切过 | 升级到 v7.3（启动时自动 `SUBSTR(rec_time,1,8)`）；也可直接跑 `python _scaffold\audit_rec_time.py --apply` 手工裁 |
| **同一笔操作，界面上的数字变了两次（比如刚加完是 900，过一会儿变成 1000）** | v7.3 及以前有 6 处写库入口绕过了统一收尾 `refresh_after_change()`（待还款合计两条路径、新增账户、编辑初始余额、删除账户、从备份恢复）——写完只刷列表，余额与余额快照等下一次别的操作才被动重算，于是「先显示旧数、再跳成新数」 | 升级到 v7.4。升级后这 6 处写完全部当场全量对账，一次到位 |
| **新增 / 删除账户、或改了初始余额后，「余额统计」页的总数没跟着变** | v7.3 及以前这三处只刷账户表，不重算余额快照；而快照 = 所有账户初始余额之和 + 截至当日净额，初始余额合计变了快照就永久偏 | 升级到 v7.4（三处都走 `refresh_after_change()`）。若历史上已留下错的快照，升级后随便做一个写操作（或重开程序）就会按公式重算正确 |
| **「余额统计」页的总数，和「账户结余」页各账户加总对不上（通常差一笔借款）** / 新建账户结余算出 -1016.46 这种负数 | v7.4 及以前，一条还款算哪个账户只看它自己记的 `account_id`；早年「一键批量还款」把这个字段写成 `-1`，那笔钱两头都不算，于是全库净额 0.00、账户净额 -1016.46 | 升级到 v7.5：所有账户口径改按「有效账户归属」（还款跟着它偿还的那笔借款走），启动时还会把历史快照从 `0000-01-01` 全量重算一遍。**登记数据一个字不动** |
| **某天的记录怎么都查不出来 / 按月统计突然变 0** | 正常情况下不会发生：`date` 列永远是纯 `2026-11-21`，时间单独存 `rec_time`。如果你手工改过库、把时间拼进了 `date`，就会这样 | 用 D 条 SQL 查 `date` 长度不是 10 的记录，改回 `YYYY-MM-DD`，时间挪进 `rec_time` |
| **记录几百上千条，找不到人，也不记得上次看到哪了** | v7.5 及以前主列表一次性把所有记录画出来，没有分页，也没有「上次看到第几行」的记忆 | 升级到 v7.6：表格下方分页条可翻页，默认每页 100 行（可选 20/50/100/200/500），关程序会记住你看到的那一行，下次打开自动回去 |

| **一在搜索框里打字就报 `no such column: a.name`** | v7.5 的 Bug：账户名已改成标量子查询，但搜索条件里还留着一句 `a.name LIKE ?`，旧的 JOIN 已删 → 该列不存在 | 升级到 v7.6；临时办法是不用搜索框、改用筛选面板 |

**排查步骤（照着做）**：

1. **先跑对账 SQL**：见 [5.3.3 对账自检](#533-对账自检怀疑数字不对时先跑这个)，三条不变式必须全部成立。哪条不成立，问题就在那一层（A 是单账户、B 是总账、C 是脏数据）。
2. **跑只读体检**：在项目目录执行
   ```bash
   python _scaffold\audit_all_dbs.py
   ```
   它会把本机所有 `finance_*.db` 逐个按三条不变式复核，**只读、不写库**，直接告出是哪个库、哪个账户、差多少。
3. **有脏数据就归位**：
   ```bash
   python _scaffold\fix_legacy_account_id.py            # 演练，只打印不改
   python _scaffold\fix_legacy_account_id.py --apply    # 真改（写前自动整库备份到 backups\）
   ```
   脚本会自己钉住 `initial_balance`（用归位前的余额倒推），所以**先归位还是先开程序都不影响结果**。
4. **实在救不回来**：账户表里手工把余额改对，然后**立刻**记一笔「余额」或「账户结余」类型的记录留档；下次重算会以「初始余额 + 流水」为准，手工改的 `balance` 会被覆盖——所以正确的救法是把 **初始余额** 改成能让公式成立的数，而不是改 `balance`。

**为什么「手工改 balance 会被覆盖」？** 因为 v6.9 起 `balance` 是**计算结果**，不是输入项。真正的输入是 `initial_balance`（你在账户编辑框里填的那个「余额」实际写的就是它）。想让账户余额变成 X，就算出让 `initial_balance + 流水净额 = X` 的初始余额填进去。

## 附录 C：数据库结构速查

见 9.4 节。

**常用 SQL**：

```sql
-- 看所有交易
SELECT * FROM transactions ORDER BY date DESC;

-- 看本月支出
SELECT SUM(amount) FROM transactions
WHERE type='expense' AND strftime('%Y-%m', date)='2026-09';

-- 看待还款借款
SELECT * FROM transactions
WHERE type='借款' AND status='pending';

-- 看某借款的还款记录
SELECT * FROM transactions
WHERE type='还款' AND related_id=1;

-- 看所有设置
SELECT * FROM settings;

-- 改设置
INSERT OR REPLACE INTO settings (key, value) VALUES ('scroll_bottom_after_add', '1');

-- ===== 余额对账（★ v6.9 新增，三条必须全部成立） =====
-- A. 每个账户：balance 必须 == initial_balance + 该账户流水净额
SELECT a.id, a.name, a.balance, IFNULL(a.initial_balance,0) AS initial,
       IFNULL((SELECT SUM(CASE type WHEN 'income' THEN amount WHEN '还款' THEN amount
                                 WHEN 'expense' THEN -amount WHEN '借款' THEN -amount ELSE 0 END)
               FROM transactions t WHERE t.account_id=a.id
                 AND t.type IN ('income','expense','借款','还款')),0) AS flow,
       IFNULL(a.initial_balance,0) + IFNULL((SELECT SUM(CASE type WHEN 'income' THEN amount
                 WHEN '还款' THEN amount WHEN 'expense' THEN -amount WHEN '借款' THEN -amount
                 ELSE 0 END) FROM transactions t WHERE t.account_id=a.id
                 AND t.type IN ('income','expense','借款','还款')),0) AS should_be
FROM accounts a;

-- B. 总账：SUM(balance) 必须 == SUM(initial_balance) + 全库流水净额
SELECT (SELECT SUM(IFNULL(balance,0)) FROM accounts) AS sum_balance,
       (SELECT SUM(IFNULL(initial_balance,0)) FROM accounts) AS sum_initial,
       (SELECT IFNULL(SUM(CASE type WHEN 'income' THEN amount WHEN '还款' THEN amount
                        WHEN 'expense' THEN -amount WHEN '借款' THEN -amount ELSE 0 END),0)
        FROM transactions WHERE type IN ('income','expense','借款','还款')) AS net_flow;

-- C. 有没有写错的还款记录（正常应返回 0）
SELECT COUNT(*) FROM transactions
WHERE type='还款' AND (account_id IS NULL OR account_id <= 0);

-- D. 某笔借款的已还金额与剩余应还
SELECT l.id, l.amount AS loan_amount,
       IFNULL((SELECT SUM(amount) FROM transactions r
               WHERE r.type='还款' AND r.related_id=l.id),0) AS repaid,
       MAX(0, l.amount - IFNULL((SELECT SUM(amount) FROM transactions r
               WHERE r.type='还款' AND r.related_id=l.id),0)) AS remaining
FROM transactions l WHERE l.type='借款';

-- E. 日期列是否被写脏（正常应返回 0；长度必须都是 10 的 YYYY-MM-DD）
SELECT COUNT(*) FROM transactions WHERE LENGTH(date) <> 10 OR date LIKE '% %';

-- F. 时间列格式（正常应返回 0；必须是 HH:MM:SS 八位，v7.3 起秒 2 位）
SELECT COUNT(*) FROM transactions
WHERE rec_time IS NOT NULL AND TRIM(rec_time) <> ''
  AND (LENGTH(TRIM(rec_time)) <> 8 OR TRIM(rec_time) NOT GLOB '[0-9][0-9]:[0-9][0-9]:[0-9][0-9]');

-- G. ★v7.5 有效账户归属对账：whole_db 与 per_account 必须相等（差 0.00）
--    口径：type='还款' 且有 related_id 时，归属到「它偿还的那笔借款」所在账户
WITH eff AS (
  SELECT amount, type,
         CASE WHEN type='还款' AND related_id IS NOT NULL
              THEN IFNULL((SELECT l.account_id FROM transactions l
                           WHERE l.id=transactions.related_id AND l.type='借款'), account_id)
              ELSE account_id END AS eff_account_id
  FROM transactions WHERE type IN ('income','expense','借款','还款')
)
SELECT (SELECT IFNULL(SUM(CASE type WHEN 'income' THEN amount WHEN '还款' THEN amount
                       WHEN 'expense' THEN -amount WHEN '借款' THEN -amount ELSE 0 END),0)
        FROM eff) AS whole_db,
       (SELECT IFNULL(SUM(net),0) FROM (
          SELECT (SELECT IFNULL(SUM(CASE e.type WHEN 'income' THEN e.amount WHEN '还款' THEN e.amount
                                   WHEN 'expense' THEN -e.amount WHEN '借款' THEN -e.amount ELSE 0 END),0)
                  FROM eff e WHERE e.eff_account_id = a.id) AS net
          FROM accounts a)) AS per_account;

-- H. ★v7.5 历史遗留清单：还款记在了和借款不同的账户上（升级后计算已不受影响，仅用于了解历史）
--    返回的记录是早年「一键批量还款」写错 account_id 的历史遗留：v7.5 起计算已自动归位，
--    所以「有记录」不代表算错；本机实测 李红玲20251017.db=0 行、李红玲（结束20251016）.db=57 行
SELECT r.id, r.date, r.amount, r.account_id AS repay_account, l.id AS loan_id, l.account_id AS loan_account
FROM transactions r JOIN transactions l ON l.id = r.related_id AND l.type = '借款'
WHERE r.type = '还款' AND IFNULL(r.account_id, -99999) <> IFNULL(l.account_id, -99999)
ORDER BY r.date, r.id;
```

> 三条不变式 A / B / C 的完整说明见 [5.3.3 对账自检](#533-对账自检怀疑数字不对时先跑这个)。
